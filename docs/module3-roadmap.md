## 1. 项目全貌

面向老年康养的“数据—模型—服务—终端”闭环平台，目标是让居家、社区、机构三类养老场景共享同一套数据与智能服务。

四个板块的分工：

| 板块 | 角色 | 核心产出 |
| --- | --- | --- |
| 1. 康养垂直大模型 | 大脑 | 本地知识库、RAG 增强、持续微调 |
| 2. 个性化实时推送 | 神经反馈 | 穿戴/行为数据、异常剔除、用户画像、精准推送 |
| 3. 电子健康档案集成平台 | 记忆与档案中枢 | 多源接入、标准化存储、档案融合、开放服务 |
| 4. 机器人与智能终端接口 | 手脚 | 终端接入、协议抽象、硬件控制 |

闭环流程：

```text
穿戴设备 / 医院系统 / 社区随访 / 纸质报告
        ↓
第三板块：接入 → 转换映射 → 多源融合 → 统一电子健康档案
        ↓
第一板块：RAG 检索 + 垂直大模型评估
        ↓
第二板块：生成个性化建议并实时推送
        ↓
第四板块：终端/机器人执行提醒、问询、护理服务
        ↓
交互数据回流第三板块，形成持续学习闭环
```

最终产品形态：

- 老人/家属：健康提醒、用药提醒、异常预警、康养建议。
- 医生/护理员：完整档案、时间线、风险提示、随访建议。
- 机构管理员：数据源管理、映射配置、权限管理、审计、数据质量看板。
- 科研人员：脱敏数据、标注数据、映射/融合/上下文评测。

## 2. 第三板块的定位、职责与边界

### 2.1 定位

整个项目的数据底座和交换中枢。负责把异构健康数据变成**标准化、可追溯、可分权共享**的电子健康档案，并以 API/事件供其他板块使用。

### 2.2 六个环节

对应项目结构图：

1. **档案标准建模**：用 OpenEHR 双层建模定义老年康养档案模板（基础信息、体征、慢病、过敏、用药、评估、随访、检验检查等）。
2. **结构化数据存储**：临床记录以 COMPOSITION/观测数据形式持久化，可查询、可版本追溯。
3. **异构数据接入**：对接医院 HIS/区域平台、社区随访、体检系统、穿戴设备、纸质/PDF/图片资料。
4. **中间件转换映射**：字段映射、单位归一、时间归一、术语映射（LOINC/ICD-10）、校验、来源标记。
5. **多源档案融合**：患者主索引（EMPI）、去重、冲突消解、统一时间线、来源溯源。
6. **多用户分权查看**：角色与患者级授权、脱敏、审计、导出/共享控制。

### 2.3 对外能力

- 统一档案 API：给板块 1 组装 LLM 上下文；给板块 2 提供风险标签与时间线；给板块 4 提供老人基础信息。
- 变更事件：`composition.created/updated`、`document.parsed` 等，供其他板块增量消费。
- 档案交换：导入/导出/跨机构共享。
- 数据质量统计：接入量、映射成功率、完整率、响应时间。

### 2.4 明确不负责

- 不训练大模型，不做 RAG 检索策略（板块 1）。
- 不做推送文案与推送策略（板块 2）。
- 不做机器人协议适配与硬件控制（板块 4）。
- 第三板块只保证数据干净、完整、可追溯、可安全调用。

## 3. 当前 MVP 现状

### 3.1 技术栈

FastAPI + Jinja2 + SQLite，单机运行。

### 3.2 已实现

- 患者基础档案与就诊记录管理（列表/新增/时间线）。
- 简化 OpenEHR 双层建模，3 个老年康养模板。
- COMPOSITION 版本管理，可查看历史版本。
- 附件上传/下载/删除，文本类文件自动抽取内容。
- OpenEHR JSON 导入/导出。
- 结构化 + 非结构化上下文组装，`/api/ask` 接大模型或本地兜底。

核心文件：

| 文件 | 作用 |
| --- | --- |
| `app/main.py` | FastAPI 路由 |
| `app/db.py` | SQLite 连接、表结构、示例数据 |
| `app/openehr.py` | OpenEHR 简化模型、模板、版本、导入导出 |
| `app/attachments.py` | 附件存储与文本抽取 |
| `app/llm.py` | 大模型上下文组装与调用 |

### 3.3 冒烟测试结果（2026-10-22）

已跑通：

- 患者列表、患者详情。
- OpenEHR 记录新增、版本历史。
- 档案导出。
- `/api/patients/{id}/context`、`/api/ask`。
- 附件上传（普通文件）。

实测问题：

1. **中文文件名附件下载 500**：`app/main.py` 使用 `Content-Disposition: attachment; filename="中文"`，HTTP 头需 latin-1，必须改 RFC 5987（`filename*=UTF-8''...`）。
2. **重复患者编号 500**：`app/main.py` 未捕获 SQLite 唯一约束异常。
3. **导出/导入丢附件**：`app/openehr.py` 的 `import_ehr` 不处理 attachments；导出也不含附件二进制，交换不完整。
4. **空版本记录被静默跳过**：导入时 `versions` 为空直接 `continue`，数据无提示丢失。
5. **数据库连接不关闭**：`app/db.py` 的 `with get_db()` 只提交事务，未 `close()`。
6. **上传无大小限制、整文件读入内存**：`app/main.py` 的 `await file.read()`。
7. **LLM 同步调用阻塞事件循环**：async 路由里调用同步 urllib，超时 30 秒。
8. **无登录、无权限、无审计**；患者 PII 原样发给外部大模型。
9. **就诊数据两套并存**：`encounters` 表与 `encounter.v1` 模板重复，统计和交换口径不一致。
10. **`attachments.composition_uid` 字段已建但从未使用**。

## 4. MVP 与第三板块的差距

当前 MVP 是第三板块的一个**纵向技术切片**，不是缩小版平台。

| 维度 | 当前 MVP | 第三板块目标 |
| --- | --- | --- |
| 数据来源 | 手工表单 + 附件 | 医院、社区、设备、文档多源自动接入 |
| 数据转换 | 表单字段直接入库 | 配置化映射、校验、单位/术语归一 |
| 患者归并 | 人工建患者 | 患者主索引、多源匹配、去重合并 |
| 非结构化 | 仅文本类抽取 | PDF/OCR/ASR 统一转文本 |
| 存储 | SQLite 单机 | 可扩展数据库 + 原始数据留痕 |
| 权限 | 无 | 多角色、患者级授权、审计 |
| 对外接口 | 少量查询接口 | 稳定 API + 事件 + 交换标准 |
| 目标 | 证明“能建、能存、能查、能问” | 支撑“多源、多用户、可科研”的真实平台 |

完成度判断：MVP 约完成第三板块的 30%—40%，缺的正是结构图中间的“异构接入、转换映射、多源融合、分权查看”。

## 5. 目标架构

### 5.1 数据链路

```text
外部数据源
  → 接入适配器（parse）
  → 原始数据落地（raw_records，保留哈希与报文）
  → 映射/校验/归一化（mapping）
  → OpenEHR COMPOSITION / 文档记录
  → 统一档案（结构化 + 非结构化）
  → 服务层（API / 事件 / 权限 / 审计）
  → 板块 1 / 2 / 4
```

### 5.2 分层

1. **接入层**：CSV/Excel、FHIR/HL7 v2、设备 HTTP/MQTT、PDF/图片/音频。
2. **标准化层**：映射配置、术语映射、单位/时间归一、患者主索引、融合与质量评估。
3. **存储层**：原始层、规范层、文档层、版本/审计层。
4. **服务层**：档案 API、上下文 API、事件、分权、审计、交换。

### 5.3 建议目录结构

```text
app/
  ingest/
    base.py            # SourceAdapter 接口
    csv_source.py      # CSV/Excel 适配器
    fhir_source.py     # FHIR/HL7 适配器
    device_source.py   # 设备/穿戴适配器
  mapping/
    engine.py          # 映射执行器
    rules/             # YAML/JSON 映射配置
    terminology.py     # LOINC/ICD-10 等术语映射
    validate.py        # 校验与单位归一
  services/
    empi.py            # 患者主索引与融合
    timeline.py        # 统一时间线
    documents.py       # 文档解析管线
    export.py          # 交换与打包
  api/
    ingest.py
    ehr.py
    documents.py
    admin.py
  auth/
    users.py
    permissions.py
    audit.py
workers/
  parse_document.py    # PDF/OCR/ASR 后台任务
migrations/
tests/
docs/contracts/        # OpenAPI 契约
```

### 5.4 需要新增的数据表

| 表 | 用途 |
| --- | --- |
| `source_systems` | 数据源注册（医院、社区、设备等） |
| `patient_external_ids` | `(source_system, external_id) → patient_id`，多源融合关键 |
| `ingest_jobs` | 每次导入任务、状态、统计、错误 |
| `raw_records` | 原始报文、哈希、来源、处理状态，支持重放 |
| `mapping_rules` | 配置化字段/术语映射 |
| `patients` / `ehrs` / `compositions` | 现有档案主链，保留 |
| `documents` 或扩展 `attachments` | 文档元数据、解析状态、抽取文本、版本、哈希 |
| `users` / `roles` / `patient_access` | 多用户分权 |
| `audit_logs` | 查看/修改/导出/AI 调用审计 |
| `data_quality_reports` | 映射准确率、完整率等指标 |

### 5.5 外部接口契约（建议先冻结）

1. **接入契约**

```http
POST /api/ingest/{source_type}
{
  "source_system": "his_a",
  "external_patient_id": "H000123",
  "observed_at": "2026-10-22T09:00:00",
  "schema_version": "1.0",
  "payload": { }

```

2. **查询契约**

3. **变更事件**

- `composition.created` / `composition.updated`
- `document.parsed` / `document.failed`
- `patient.merged`

1. 同一患者从 3 类异构源接入，自动归并，时间线完整，可看来源。
2. 结构化记录可版本追溯，导出再导入不丢数据。

4. 医生/照护者/管理员看到的数据范围不同，操作有审计。
5. 板块 1 能通过稳定 API/事件拿到增量档案，不直接读数据库。

### 暂不做

## 7. 科研方向

MVP 是实验平台，科研要围绕平台中的真实难题做算法、标准和评测，避免只停留在“做了一个系统”。

### 主方向 1：多源异构健康数据的语义映射与标准化

- 问题：不同医院、社区、设备的字段、编码、单位、时间粒度不一致。
- 内容：规则 + 大模型自动生成映射；LOINC/ICD-10/康养术语映射；单位/时间归一；专家反馈主动学习；准确率与可解释性评测。
- 产出：映射中间件、映射准确率 ≥90% 实验报告、论文/专利、数据交换规范。
- 定位：第三板块最核心、最容易积累技术壁垒的方向。

### 主方向 2：多源档案融合与患者主索引

- 问题：同一老人在不同系统有不同 ID，如何安全识别并融合成可信时间线。
- 内容：隐私保护的患者匹配；去重与冲突消解；带来源可信度和不确定性的融合；时序对齐与缺失处理。
- 产出：EMPI/档案融合模块、融合质量评测、论文/专利。

### 主方向 3：面向大模型/RAG 的电子健康档案上下文工程

- 问题：档案长且杂，如何组织给大模型，控制 token、保证证据可追溯、减少幻觉。
- 内容：面向 LLM 的档案摘要与时序压缩；证据溯源；结构化 + 非结构化上下文融合排序；上下文质量对评估准确率的影响。
- 产出：EHR Context API、评估基准、与板块 1 的联合论文。
- 定位：与板块 1 协作最紧密，也是第三板块对整体项目最直接的贡献。

### 支撑方向 1：多模态健康数据统一

PDF、检验单图片、语音随访、设备信号转统一临床概念。先做工程管线，再研究 OCR 纠错、医学实体抽取、多模态对齐。与板块 1、2 协作。

### 支撑方向 2：可信共享与隐私保护

患者级分权、脱敏、审计、知情同意、跨机构安全交换。适合形成软件著作权、行业标准、白皮书，支撑“数据安全合规”。

### 科研节奏

- 0—3 个月：打通主链，形成可演示平台（3 类源 → 统一档案 → API 给板块 1）。
- 3—6 个月：主攻语义映射 + 患者主索引，积累评测数据与论文素材。
- 6—12 个月：面向 LLM 的档案上下文 + 多模态统一，与板块 1 联合实验。
- 持续：沉淀老年康养 EHR 数据集、映射规则库、评测基准、标准文档。

### 一句话总结

> MVP 证明“能存、能看、能问”；第三板块要解决“多源能进、语义能通、档案能信、多方能共用”；科研围绕“映射、融合、面向大模型的档案表示”形成可发表、可申请专利、可写标准的成果。

## 2026-11-26 决策记录：V0.3 任务二 标准化接入与时间语义

- `app/ingest.py` 在导入数值字段时调用 `app/dictionary.py`，不再使用简单 `factors` 倍率；`mappings.json` 的 `metrics` 声明标准指标编码和来源单位。
- `metrics` 的 `code` 必须与模板字段对应的字典编码一致，否则该行失败；未显式配置时默认按字典标准单位处理。
- 换算后的标准值写入 COMPOSITION items；COMPOSITION 增加 `normalization`，保存 metric_code、raw_value、raw_unit、standard_value、standard_unit、plausible，原始值始终可从 `raw_records` 追溯。
- 时间语义明确为：`observed_at` 测量时间、`recorded_at` 入库时间、`updated_at` 更新时间；`record_origins` 新增 `recorded_at/updated_at` 并做旧库补列迁移。
- 异常值只标记（ok/below_range/above_range），不删除、不自动修正；非法数值、未知指标、不支持单位按行失败并返回明确原因。
- 启动时执行 `ingest.validate_rules()`，校验来源模板、字段、指标编码和单位；`GET /api/ehr/{id}/provenance/{uid}` 返回 `normalization`。
- 扩展测试覆盖单位换算、非法数值、未知指标、不支持单位、重复导入、时间字段和来源追溯；不引入新依赖，不 git commit。
